## Round 5 新增修复（本次对话）

### P1.5 — `_is_table_only_chunk` 未检测 Markdown `|` 表格

**文件**：`finetune/test/test_filter.py`

**问题**：原函数只检测 `\t` 和 `</td>` 风格的表格，Markdown pipe 表格（`| 列1 | 列2 |`）不会被过滤，导致纯表格 chunk 进入问题生成流程，浪费全链路 LLM 调用并产生低质量 QA。

**改动**：
- 新增两个编译正则 `_MD_PIPE_ROW_RE`（匹配含 `|` 的行）和 `_MD_PIPE_SEP_RE`（匹配 `|---|` 分隔行）
- 在 `_is_table_only_chunk` 末尾加判断：pipe 行占比 > 60% 且有 ≥1 条分隔行且字符总数 < 1200 → 返回 True
- 同步更新 docstring

### P1.7 — `force_rewrite=True` 答案精炼后无元信息兜底过滤

**文件**：`finetune/test/test_filter.py`

**问题**：`AnswerCritiqueEvaluator`（Step 5）标记 `force_rewrite=True` 的行经 `AnswerRefiner`（Step 6）精炼后，可能仍输出含 OUTOFSCOPE 或元信息托词的答案，直接流入 Step 7 QuestionRefiner 和 Step 8 Rubric，浪费后续 LLM 调用。

**改动**：
- 新增行级过滤谓词 `_refined_answer_valid(row)`：调用 `is_outofscope_or_meta_tox` 对 `refined_answer` 做廉价检测
- 在 Step 6 `AnswerRefiner.run()` 调用之后插入 `storage_apply_row_mask(s.step(), _refined_answer_valid)`

**说明**：此修复属于廉价兜底（无 LLM 调用）；深度溯源问题（ungrounded content）仍由 Rubric SC-1 ≥ 3 门槛负责淘汰，两者互补。

### P2.11 — Grounding REWRITE 判定标准包含纯格式问题「结构混乱」

**文件**：`DataFlow/dataflow/prompts/tech_doc_qa.py`（`AnswerGroundingFilterPrompt`）

**问题**：原 REWRITE 标准包含"答案结构混乱但原文中有对应内容"，这是排版问题，不是事实溯源问题，会触发不必要的 `AnswerRewriter` LLM 调用，同时与 REWRITE 的语义（"内容不可信、需改写"）不符。

**改动**：移除该条 REWRITE 标准，保留：
- "答案方向正确，但加入了原文不支持的具体细节"
- "答案在原文基础上过度扩写"

### P3-A — KEEP 行 `anchor_sentences` 只有 1 句（质量低于 REWRITE 行）

**文件**：
- `DataFlow/dataflow/prompts/tech_doc_qa.py`（`AnswerGroundingFilterPrompt`）
- `DataFlow/dataflow/operators/text_sft/tech_doc/answer_rewriter.py`（`AnswerRewriter`）

**问题**：
- KEEP 行：`anchor_sentences` 来自 `grounding_result["original_evidence"]`（单字符串，最多 1 句）
- REWRITE 行：`anchor_sentences` 来自 Rewriter JSON 输出（多句列表）
- KEEP 行（溯源质量更好）反而提供给 RubricScorer 的 anchor 上下文更少，SC-1 评分可能偏低。

**改动**：
1. `AnswerGroundingFilterPrompt.build_prompt` 的 JSON 输出格式中，将 `"original_evidence": "..."` 替换为 `"anchor_sentences": ["支撑句1", "支撑句2"]`，与 Rewriter 输出格式统一。
2. `AnswerRewriter.run()` KEEP 行处理逻辑：优先读 `gr.get("anchor_sentences")`（列表），若不存在则 fallback 到 `_evidence_to_anchors(gr.get("original_evidence"))`（向后兼容）。

### P3-B — MetaFilter 输入含重复「问题：」前缀

**文件**：`finetune/test/test_filter.py`（`storage_prepare_meta_triplet_view`）

**问题**：`storage_prepare_meta_triplet_view` 生成的 `meta_triplet_instruction` 以"问题：\n{question}"开头，而 `MetaFilter._combine_fields` 又在外层套一层 `"Question: {instruction}"` 前缀，最终 LLM 收到的是：
```
Question: 问题：
[question text]
原文支撑句：...
Context: ...
Answer: ...
```
"Question: 问题：" 是语义重复的双前缀，对中文优化模型造成不必要的语言混用噪音。

**改动**：`storage_prepare_meta_triplet_view` 的 `_build` 函数中，`parts` 列表的第一项从 `f"问题：\n{question}"` 改为直接的 `question` 字符串。MetaFilter 的"Question: "前缀保留，结果变为：
```
Question: [question text]
原文支撑句：...
Context: ...
Answer: ...
```

### P3-C — `差异对比` 和 `版本特性` Rubric HC 类型无法被激活

**文件**：
- `finetune/test/test_filter.py`（`_DISTILL_TO_RUBRIC_QUESTION_TYPE`）
- `DataFlow/dataflow/prompts/general_text.py`（`DistillQuestionGeneratorPrompt`、`TextContentTypeAnalyzerPrompt`）

**问题**：Rubric 的 `HARD_CONSTRAINTS_BY_TYPE` 定义了 5 个专项类型，其中 `差异对比` 和 `版本特性` 在原有的 11 类 distill 轴B类型里没有对应项，导致这两个 Rubric HC 分支永远无法被激活——相关问题全部走 `default` HC。

**改动**：
1. `_DISTILL_TO_RUBRIC_QUESTION_TYPE` 新增两条映射：
   - `"DifferenceComparison"` → `"差异对比"`
   - `"VersionFeature"` → `"版本特性"`
2. `DistillQuestionGeneratorPrompt.build_prompt` 的 Constraint 5（轴B题型列表）新增两个类型：
   - `DifferenceComparison`：两个或以上方案/模式/版本的核心区别，题干须明确被对比对象，答案给出可用于选型决策的差异结论
   - `VersionFeature`：特定版本新增/变更/废弃的特性，题干须写明版本约束，答案与原文版本范围严格对应
3. Constraint 6（占比契约）为两个新类型增加使用条件和上限约束（≤20%，且仅在 context 中有明确对比结构或版本号时可用）
4. `TextContentTypeAnalyzerPrompt` 同步更新：类型列表从 11 类扩展到 13 类，信号→题型映射规则补充对应信号描述
